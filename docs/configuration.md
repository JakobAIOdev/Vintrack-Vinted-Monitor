# Configuration

Vintrack reads deployment settings from the root `.env` through Docker Compose.
Start with:

```bash
make init
```

Treat `.env` as a secret. Never commit it or paste it into an issue.

## Required secrets

| Variable | Purpose | Example |
| --- | --- | --- |
| `AUTH_SECRET` | Signs and encrypts application authentication state | generated by `make init` |
| `VINTED_SESSION_ENCRYPTION_KEY` | Encrypts linked Vinted session data at rest | generated by `make init` |

Both values must remain stable after users or linked sessions exist. Replacing
them without a migration or recovery plan invalidates authentication state and
can make stored account sessions unreadable.

Generate values manually with:

```bash
openssl rand -base64 32
```

## Public URLs and Caddy

| Variable | Default in `.env.example` | Purpose |
| --- | --- | --- |
| `AUTH_URL` | `http://localhost:3000` | Canonical URL used by the authentication layer |
| `SEO_INDEXING_ENABLED` | `false` | Opt in to public marketing-page indexing, canonicals, and sitemap output |
| `APP_PUBLIC_URL`, `DASHBOARD_URL` | unset | Deprecated one-release fallback aliases for `AUTH_URL` |
| `VINTRACK_SITE_ADDRESS` | `http://localhost` | Caddy site address or public hostname |

For production:

```env
AUTH_URL=https://vintrack.example.com
SEO_INDEXING_ENABLED=false
VINTRACK_SITE_ADDRESS=vintrack.example.com
```

The worker resolves canonical `AUTH_URL`, then the deprecated `APP_PUBLIC_URL` and `DASHBOARD_URL` fallbacks. Values must be absolute origins and must agree when several are
configured. Production requires HTTPS and rejects local or temporary tunnel
origins; Vintrack omits dashboard buttons while configuration health is red.

Search indexing is disabled by default so self-hosted instances do not compete
with identical marketing content accidentally. Enable `SEO_INDEXING_ENABLED`
only for a deliberately public deployment with a valid `AUTH_URL`.

## Authentication

Choose Discord or OIDC as the login provider. GitHub can be connected afterwards
from **Account** for rewards; it is not a separate login method. New users start
with the `free` role. Follow the [first-admin setup](getting-started.md#5-grant-your-first-account-admin-access)
to administer a new instance.

### Discord OAuth

```env
AUTH_DISCORD_ID=your-client-id
AUTH_DISCORD_SECRET=your-client-secret
```

Configure exactly one callback for each environment:

```text
http://localhost:3000/api/auth/callback/discord
https://vintrack.example.com/api/auth/callback/discord
```

### OIDC

```env
AUTH_OIDC_ISSUER=https://identity.example.com/application/o/vintrack/
AUTH_OIDC_CLIENT_ID=your-client-id
AUTH_OIDC_CLIENT_SECRET=your-client-secret
AUTH_OIDC_NAME=Company SSO
```

Callback:

```text
https://vintrack.example.com/api/auth/callback/oidc
```

When issuer, client ID, and client secret are all present, OIDC replaces Discord.
Existing Discord identities are not automatically linked to OIDC identities.
Verify administrative access before switching an established installation.

### GitHub linking and rewards

```env
AUTH_GITHUB_ID=your-oauth-app-client-id
AUTH_GITHUB_SECRET=your-oauth-app-client-secret
GITHUB_REPOSITORY_WEBHOOK_SECRET=separate-random-secret
GITHUB_SPONSORS_WEBHOOK_SECRET=another-random-secret
GITHUB_REWARDS_MAINTAINER_TOKEN=maintainer-token
GITHUB_REWARDS_SYNC_SECRET=random-internal-bearer-secret
```

GitHub linking is available only when both OAuth values are set. Its callback is
`https://vintrack.example.com/api/auth/callback/github`. Members must
link from **Account** after signing in with Discord or OIDC. See [GitHub Login and
Rewards](github-rewards.md) for OAuth, webhook, backfill, privacy, admin policy,
and safe rollout instructions.

## Database and Redis

The provided Compose stack uses:

- PostgreSQL 15 with persistent `postgres_data`;
- Redis 7 with append-only persistence in `redis_data`;
- loopback-only host ports `5435` and `6379`;
- an explicit migration service that runs before application services.

The internal connection strings and default database credentials currently match
the Compose services. If you replace the database or Redis deployment, update
all dependent service connection strings together and validate the fully
rendered Compose configuration before restarting production.

Do not delete named volumes to troubleshoot an application issue. That removes
persistent data.

## Browser extension

```env
BROWSER_EXTENSION_LATEST_VERSION=0.3.3
BROWSER_EXTENSION_MIN_VERSION=0.2.1
BROWSER_EXTENSION_FIREFOX_URL=https://addons.mozilla.org/firefox/addon/vintrack-browser-sync/
```

`LATEST` controls the update notice. `MIN` blocks extension actions from older
clients. `LATEST` should match both extension manifests; the release workflow
checks this before deployment. `MIN` may intentionally lag behind when older
clients should remain usable. The Firefox URL points the dashboard and guide to
the public AMO listing and can be replaced after the first AMO approval if the
final listing URL differs. GitHub releases attach the Chrome ZIP. During the
same release, Firefox is published only when the manifest version has no
corresponding marker tag such as `extension-v0.1.6`.

For your own domain, follow the [self-hosted extension setup](browser-extension.md#self-hosted-domain).
These variables control compatibility notices and the Firefox download link;
they do not authorize a custom hostname in the public extension.

## Telegram

Leave all Telegram variables empty when the feature is unused:

```env
TELEGRAM_BOT_TOKEN=
TELEGRAM_BOT_USERNAME=
TELEGRAM_WEBHOOK_SECRET=
```

For an enabled bot:

1. Create a bot with [@BotFather](https://t.me/BotFather).
2. Set the bot token, public username without `@`, and a random webhook secret.
3. Ensure `AUTH_URL` is the canonical public HTTPS origin.
4. Recreate the services so they load the new settings:

   ```bash
   docker compose up -d --force-recreate control-center worker
   ```

5. Register and verify the webhook from the repository root. This reads secrets
   inside the container, keeping the bot token out of command arguments and
   shell history:

   ```bash
   docker compose exec -T control-center node --input-type=module <<'NODE'
   const { TELEGRAM_BOT_TOKEN: token, TELEGRAM_WEBHOOK_SECRET: secret, AUTH_URL: origin } = process.env;
   if (!token || !secret || !origin?.startsWith("https://")) {
     throw new Error("Set the Telegram token, webhook secret and HTTPS AUTH_URL first.");
   }
   const target = new URL("/api/telegram/webhook", origin).href;
   async function call(method, body) {
     const response = await fetch(`https://api.telegram.org/bot${token}/${method}`, {
       method: "POST", body,
     });
     const data = await response.json();
     if (!response.ok || !data.ok) throw new Error(`Telegram ${method} failed; check the bot settings.`);
     return data.result;
   }
   await call("setWebhook", new URLSearchParams({ url: target, secret_token: secret }));
   const info = await call("getWebhookInfo");
   if (info.url !== target) throw new Error("Telegram webhook URL does not match AUTH_URL.");
   console.log("Webhook registered:", info.url);
   console.log("Pending updates:", info.pending_update_count);
   NODE
   ```

   Generate `TELEGRAM_WEBHOOK_SECRET` with `openssl rand -hex 32`. This uses
   Telegram's documented [webhook API](https://core.telegram.org/bots/api#setwebhook).
   A bot can have only one webhook; use a separate bot for separate instances.

The webhook target is:

```text
https://vintrack.example.com/api/telegram/webhook
```

Users connect through a generated one-time command. They do not need access to
the bot token or a numeric chat ID.

Users can choose `Rich` or `Compact` item alerts in **Dashboard settings**.
Message styles are account-wide but configured independently for Discord and
Telegram; the default remains `Rich` for both channels.

## Proxy sources

Vintrack can use:

- **personal groups** created by a user in the dashboard;
- **server proxies** configured by the operator;
- a shared, optional **Free Proxy Pool** managed by the proxy-maintainer worker.

Static server proxies live in `apps/worker/proxies.txt`, one per line:

```text
http://user:pass@host:port
https://user:pass@host:port
socks4://user:pass@host:port
socks5://user:pass@host:port
host:port:user:pass
```

The **Admin → System** server-proxy setting takes precedence over this file
when present, including an empty setting. The file is the startup fallback;
restart the worker after file changes. Personal groups are configured separately.
The file is intentionally ignored by Git. Do not commit proxy credentials.
Vinted UK monitoring requires IPv4 proxies.

Shared public proxies are volatile and should not be treated as guaranteed
capacity. Configure imports, regions, thresholds, and pool availability in the
admin settings, and use owned capacity for sustained deployments.

### Choosing a provider

Vintrack does not require a specific proxy vendor. Match the provider's proxy
type and regions to the formats above and test with conservative monitor
intervals before adding production capacity.

The maintainer currently uses
[Webshare Proxy Server](https://www.webshare.io/?referral_code=qhu9q567qrqp),
which may include limited free proxies for initial testing. This is a referral
link that may support Vintrack at no additional cost to you; Webshare remains
entirely optional.

The [Proxy6 checker](https://proxy6.net/checker) can be used for a basic
connectivity check. It is a third-party service: review its privacy policy and
do not submit reusable proxy credentials unless you trust its handling.

## Price Watch polling

Price Watch separates canonical targets from polling schedules. Shared watches
deduplicate by `(region, item)` and use the fastest booked interval; personal
proxy schedules are isolated by `(item, proxy group)`. Shared presets are 2–60
minutes, while a region-verified group with working proxies unlocks presets from
30 seconds. Activation and role access live under **Admin → Features**. Runtime floors and request budgets live under **Admin → Operations → Price Watch**
and are reloaded by workers about every 10 seconds.

```env
PRICE_WATCH_WORKERS=4
PRICE_WATCH_TRANSPORT_MODE=auto
PRICE_WATCH_CLIENT_POOL_SIZE=4
PRICE_WATCH_TIMEOUT_MS=6000
PRICE_WATCH_HTML_LIMIT_BYTES=3145728
```

Transport modes:

- `auto` uses the health-aware server proxy pool; only development installs may
  fall back to the server's direct connection;
- `direct` is a development option and is overridden in production;
- `proxy` strictly requires the server proxy pool and never exposes direct
  egress as a fallback.

Production shared polling always requires reliable server proxies. Personal
schedules use only the selected verified group and never fall back to server or
direct traffic. Free public proxies are not used for Price Watch polling. Set
`AUTH_URL` to the public HTTPS origin so Discord and Telegram alerts can
link directly to the corresponding Price Watch.

## Worker behavior

Deployment-bound worker settings (discovery, enrichment and latency switches are managed under **Admin → System → Worker Policy**):

| Variable | Default | Description |
| --- | ---: | --- |
| `VINTED_FETCH_MODE` | `live` | Use `mock` only for development |
| `CLIENT_POOL_SIZE` | `5` | Dedicated catalog client pool |
| `FREE_PROXY_CLIENT_POOL_SIZE` | `50` | Regional free-proxy sessions shared by monitors |
| `TLS_PROFILE` | `chrome_146` | TLS client profile |
| `CATALOG_TIMEOUT_MS` | `2000` | Canonical catalog request timeout |
| `CATALOG_HEDGE_DELAY_MS` | `250` | Delay before a secondary attempt |
| `FREE_PROXY_CATALOG_HEDGE_DELAY_MS` | `900` | Less aggressive hedge delay for public proxies |
| `CATALOG_MAX_ATTEMPTS` | `5` | Bounded request attempts |

Change concurrency only after observing database, Redis, proxy, and upstream
behavior. More workers do not automatically improve useful throughput.

See [Worker speed and hybrid discovery](worker-speed.md) for the full rollout
model and [Pre-index shadow scanner](preindex-shadow.md) for the isolated
experiment.

## Retention and maintenance

The proxy-maintainer worker also performs bounded cleanup:

| Variable | Default |
| --- | ---: |
| `MONITOR_RUN_RETENTION_HOURS` | `24` |
| `MONITOR_RUN_STATS_RETENTION_DAYS` | `90` |
| `DETECTION_RETENTION_DAYS` | `14` |
| `PREINDEX_PROBE_RETENTION_HOURS` | `48` |
| `PREINDEX_SAMPLE_RETENTION_DAYS` | `14` |

Review storage requirements before increasing retention.

## Experimental pre-index scanner

The scanner is opt-in and shadow-only:

```env
COMPOSE_PROFILES=preindex
ID_SCANNER_ENABLED=true
```

It does not send alerts. Read [Pre-index shadow scanner](preindex-shadow.md)
before enabling it.
